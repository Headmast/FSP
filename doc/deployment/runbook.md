# Публикация и восстановление демо

Текущее состояние после OPS-001: MVP работает на digitarium через Pinggy free. [Постоянная страница LLM Love](https://llmlove.ru/dreamwork/fsp-demo.html) показывает текущий адрес MVP и прототипа; cron раз в минуту восстанавливает истёкший туннель. Инструкция установки и проверки — [watchdog](watchdog.md), [фактические результаты](../qa/watchdog-results.md).

## Окружение и каталоги

Проверенный сервер: Debian 13, Python 3.13.5, около 1 ГБ RAM, Git; Docker отсутствует, nginx обслуживает другие приложения. Перед новым выпуском проверить окружение. Используется SSH alias digitarium; существующий nginx и другие процессы не меняются.

`~/fsp-mvp/releases/<SHA>` содержит неизменяемый код; `current` указывает на выбранный релиз. `shared` хранит .env, SQLite, backup, логи, PID, maintenance.lock и инструменты cron. База и секреты не входят в Git и HTTP артефакт. .env и конфигурация FTPS имеют права 0600.

Gunicorn слушает только `127.0.0.1:8011`, один worker / четыре threads, стандартный keep-alive. Django: DEBUG=0, secure cookies, HSTS 3600, точный host/origin текущего туннеля без wildcard; X-Forwarded-Proto доверяется локальному туннелю. SQLite использует WAL/IMMEDIATE.

## Выпуск точного коммита

```sh
python3 scripts/deploy_mvp.py --ref <проверенный-SHA>
```

Скрипт отправляет Git архив коммита, устанавливает зависимости по uv.lock через uv 0.12.17 и Python 3.13. Перед изменением сервера получает shared maintenance lock, чтобы cron и ручной выпуск не меняли процессы одновременно. Проверяет принадлежность управляемых PID по /proc и каталогу releases; чужие процессы не останавливает.

До переключения: корректный SQLite backup, миграции, collectstatic, синтетическое seed_demo. После переключения current запускается Gunicorn отдельной группой процессов; база/секрет остаются shared. При прерывании выпуска повторить команду с проверенным SHA и исследовать причину. Watchdog восстанавливает текущую установленную версию; он не устанавливает зависимости и не выполняет миграции вместо деплоя.

`check --deploy` на проверенном релизе выдавал только W005/W021: includeSubdomains/preload выключены для стороннего временного домена. При новой конфигурации повторить проверку и разобрать предупреждения, не переносить старый PASS автоматически.

## Проверка после выпуска

Проверить /health, /version, точный SHA, основной браузерный путь, отсутствие контактов до согласия и права HTML/PDF. Проверить внешний HTTPS после отключения SSH. Записать URL/SHA/evidence и сравнить профили/попытки/предложения до и после.

Фактические перезапуск/совместимый откат, сохранность строк и восстановление backup в изолированный файл уже проверялись; [отчёт](../qa/release-results.md) относится к указанным там SHA. Не распространять этот результат на несовместимые миграции.

## Cron и текущий адрес

Установленный user cron запускает `shared/tools/maintain_demo.py` каждую минуту. Он использует тот же lock, проверяет управляемые процессы, заменяет истёкший туннель, обновляет точные ALLOWED_HOSTS/CSRF_TRUSTED_ORIGINS, перезапускает текущий релиз при необходимости и публикует статус через FTPS. Секрет подключения берётся из серверной конфигурации вне Git. Подробности — [watchdog](watchdog.md).

Страница входа стабильна, домен приложения вращается. После смены домена пользователь входит заново. Старый статус на странице отключает ссылки. Первый визит через Pinggy может показать внешний экран Enter site.

Обычное истечение адреса не требует повторного деплоя. Ручной деплой остаётся fallback при неуспешном автоматическом восстановлении. Сам cron активен/enabled, но реальная перезагрузка VPS ещё NOT_RUN. После OPS-002 watchdog дополнительно проверяет health БД и отрисованную страницу входа; изменения применяются при контрольном выпуске. Reboot — отдельная OPS-003 в [списке продолжения](../plan/remaining-work.md).

## Прототип

Канонический источник — prototype/. Сейчас прототип доступен через `/static/prototype/index.html` на текущем MVP адресе: WhiteNoise публикует только его файлы, без doc/, базы и исходников Django. Эта ссылка обновляется вместе с адресом приложения на LLM Love.

Первоначальный автономный прототип на порту 8010 публиковался через localhost.run после неудачных Cloudflare испытаний; затем старый URL стал возвращать 502. Его скрипт `scripts/deploy_prototype.py` остаётся отдельным инструментом. История и доказательства — [P0](../qa/prototype-results.md), [финальный прототип](../qa/prototype-final.json). Актуальный вход следует брать со страницы LLM Love.

## Откат и резервные копии

Для совместимого отката выполнить deploy_mvp.py с прежним проверенным SHA; сохранить backup и проверить /version/основной путь/строки данных. Если схема несовместима назад, потребуется отдельное восстановление базы с фиксацией потери записей после backup. Не обещать сохранность более поздних записей при таком восстановлении.

Backup находится вне HTTP приложения. Проверка копии — изолированное восстановление и integrity_check; production база из копии во время прежнего испытания не заменялась.

### После появления приватности PROD-004

SQLite backup не заменяет актуальные `shared/privacy-ledger.jsonl`, `shared/privacy-floor-v1` и секретную конфигурацию. Сохранять их отдельно от откатываемой БД; не откатывать журнал/floor вместе с backup и не менять ключ идентификации при этом восстановлении. Сначала остановить только управляемое приложение под maintenance lock, восстановить выбранную БД, применить актуальные миграции и `privacy_maintenance --reconcile-only` с действующим окружением; только затем запускать Gunicorn и проверять health/версию/права. `run_app.py` повторяет reconcile перед запуском. Старые данные из backup не должны стать доступны между восстановлением и повторным применением удаления/отзыва.

Деплой отклоняет код с privacy version ниже текущего процесса или persistent floor **до остановки приложения**. Это ограничение действует даже до первого события в журнале. Откат на релиз до PROD-004 после её включения недопустим; выбирать совместимый релиз с guard, не обходить проверку удалением floor. [Правила и retention](../architecture/privacy-controls.md), [фактическое изолированное восстановление SQLite](../qa/PROD-004-restore-stage.json). Полная эксплуатационная приёмка restore/reboot остаётся OPS-003/004.

## Существующий сайт и Pages

Лендинг остаётся в корне. _config.yml исключает документацию и инструменты из стандартной Jekyll сборки; это не контроль доступа. Настройки фактической Pages публикации пока не проверены. Если сборка обходит Jekyll, использовать явный артефакт только файлов сайта; не публиковать репозиторий целиком.

## История выбора туннеля

Cloudflare не дал стабильного внешнего доступа. localhost.run непоследовательно передавал proxy headers и вызывал HTTPS redirect loop; временный keep-alive=0 причину не устранил. После перехода на Pinggy с `x:https` HTTPS/HTTP2/сквозной сценарий проверены, стандартный backend keep-alive возвращён. История предварительных FAIL сохранена в QA, а не используется как текущая конфигурация.

## Публичные материалы LLM Love

После выпуска точного SHA: `python3 scripts/deploy_public_site.py --ref <SHA>`. Скрипт публикует только явный список файлов лендинга, доступности, прототипа, мокового бота, шести видео, презентации и исследования. Каждый файл загружается во временное имя, проверяется SHA-256 обратного чтения, затем заменяется; предыдущая версия сохраняется под скрытым именем `.previous-release`. Конфигурация FTPS читается на сервере, не передаётся в аргументах и не печатается. Отчёт без секретов: shared/public-site-release.json. После этого установить watchdog текущего коммита и выполнить ручной тик.
