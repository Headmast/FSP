# Quality gates и доказательства готовности

Успешный этап заканчивается проверкой, записью результата и коммитом. Выпуск требует всех применимых обязательных gates; их нельзя отменить ради срока.

P0/G1–G6 ниже — исторический набор технического демо. Он не покрывает весь [исходный план](../sources/original-mvp-plan.md). Для найденных при аудите пропусков заведены [C1–C6 и дополнительные сценарии](../plan/remaining-work.md); актуальные C1/C2/C3 имеют PASS в пределах своих evidence, C4/C5/C6 остаются NOT_RUN. Текущая очередь — в [DOC-008](../plan/implementation-gaps-2026-10-12.md); [DOC-006](scope-current.md) сохраняет прежний срез. Старые PASS сохраняют связь со своим SHA и не переносятся автоматически на новый объём.

| Gate | Проверка | Условие PASS |
|---|---|---|
| P0 | Прототип, HTTPS, сброс, моки, коммит и push | Полный сценарий воспроизводится |
| G1 | Установка из lock, миграции, запуск в чистом worktree | Нет ручных исправлений кода |
| G2 | Роли, чужие объекты, контакты, CSRF, токены | Нет обхода прав или утечки контактов |
| G3 | Порог, области, сроки, повторы, категория | Все контрольные результаты совпадают |
| G4 | Поиск, вилка, дубликаты, принятие и отказ | Основной и негативные сценарии проходят |
| G5 | Мок помощника, метка режима, отсутствие внешних запросов, ошибка, лимит | Мок явно обозначен, основной путь работает при ошибке, лимит соблюдается |
| G6 | Нагрузка, перезапуск, SHA, запуск, откат, документы | Демо соответствует проверенному коду |

## Формат результатов

Реестр gates.json: status = NOT_RUN, PASS или FAIL. Для PASS/FAIL обязательны checked_at, commit, evidence — относительный путь к отчёту. NOT_RUN не равен PASS. При изменении затронутого поведения выполнить соответствующую проверку заново.

Отчёт содержит: ID требований и сценариев; условия и команду; ожидаемое и фактическое поведение; число успешных и неуспешных проверок; дефекты; SHA проверяемого кода. Для документирования результатов допустим отдельный следующий коммит; проверенный SHA не заменять SHA этого отчёта.

Нельзя фиксировать ключи, токены сессий или персональные данные как evidence. Сохранять очищенные логи и синтетические примеры. Метрики записывать только после фактического запуска.

## Блокирующие дефекты

Обход прав, раскрытие контактов, неверное оценивание, потеря данных, неработающий основной сценарий блокируют выпуск. С 2026-10-11 пользователь разрешил мок помощника без ключа. G5 проверяет именно этот режим; реальное API подключение не заявляется как выполненное.

Проверка документации scripts/check_docs.py проверяет локальные ссылки, обязательные документы и формат реестра. Она не проверяет приложение и не выставляет gates в PASS.

## Параметры LOAD-01

Скрипт check_load.py запускает 25 виртуальных пользователей с 25 независимыми Django сессиями на двух синтетических аккаунтах: 20 сессий работодателя выполняют по 10 поисков, 5 сессий кандидата — по 10 одинаковых безопасных сохранений профиля. Всего 250 операций, 50 записей. Барьер синхронизирует начало; авторизация исключена из латентности операций. p95 считается по ближайшему рангу; целевой предел 2 секунды. Это конкуренция сессий, не 25 уникальных кандидатов. Измерение публичного HTTPS включает задержки туннеля.

Финальный замер сохраняет отдельное HTTP соединение каждой сессии; авторизация и первоначальное соединение входят в общее время запуска, но не в p95 операций. Сохранение профиля измеряется вместе с последующим GET после redirect. Предварительный внешний FAIL сохранён отдельно; итоговый PASS получен через публичный HTTPS с тем же порогом 2 секунды.
