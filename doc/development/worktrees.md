# Работа с функциями из параллельных чатов

Каждая функция разрабатывается в собственной ветке и worktree одного репозитория. Код, документация и дополнительные промпты доступны во всех checkout через Git, без ручного копирования папок.

## Начало задачи

1. Прочитать корневой AGENTS.md, цель, архитектуру и backlog.
2. Выбрать ID задачи, зафиксировать владельца и область файлов. Если задача занята, согласовать передачу вместо второго выполнения.
3. Создать checkout от согласованного коммита: python3 scripts/worktree.py create assessment --base main --port 8021.
4. Передать параллельному чату абсолютный путь checkout, ветку, ID задачи, базовый SHA и допустимые файлы. Открытие чата в основном checkout не переключает его автоматически.
5. Выполнять Git команды внутри своего checkout. Незакоммиченные изменения основного checkout в новую ветку не переносятся.

Инструмент scripts/worktree.py использует только стандартную библиотеку Python и Git. Он не запускает приложение, не копирует секреты и не удаляет checkout.

## Изоляция

Ветки называются mvp/<name>. Checkout по умолчанию создаётся рядом с репозиторием в FSP-worktrees/<name>. У каждого свой .env.worktree, .venv и .runtime с базой, логами и PID. Эти пути исключены из Git. Общие секреты не копируются автоматически.

Порт выбирается явно и не должен совпадать с портом другого worktree. Для приложения использовать APP_PORT и DATABASE_PATH из .env.worktree; будущий Django bootstrap обязан подключить эти значения. Пока приложения нет, это подготовленные настройки, а не действующая база.

Посмотреть checkout: python3 scripts/worktree.py list. Проверить локальную конфигурацию и её изоляцию: python3 scripts/worktree.py check. Загружать переменные в bash/zsh: set -a; source .env.worktree; set +a. В основном checkout при необходимости создать собственную конфигурацию командой configure --port 8011.

## Владение общими файлами

Интегратор владеет settings, общими urls, базовыми шаблонами, зависимостями и публикацией. Другие чаты предлагают изменения этих файлов отдельно, чтобы не смешивать конфликтующие решения. Модульные миграции можно создавать в своей ветке; конфликт ветвления миграций решается перед интеграцией и проверяется на чистой базе и копии demo базы.

Дополнительные функции используют тот же процесс. Рабочие документы кладутся в doc, не в личную папку чата. Runtime базы и секреты никогда не переносятся через коммит.

## Проверка и коммит

Запустить scripts/check_docs.py и проверки затронутого модуля. Записать evidence с фактическим SHA кода. Сделать коммит завершённого этапа; у незавершённой задачи явно указать ограничения. Не включать чужие незакоммиченные файлы. Секреты и локальные runtime файлы не должны попадать в git diff --cached.

Передать интегратору ID задачи, ветку, SHA, проверки, документы и зависимости. Для внешнего ревью отправить ветку: git push -u origin mvp/<name>. Push выполняется при задаче публикации или передаче ветки; коммит сам по себе не означает push.

## Интеграция

В интеграционном checkout проверить чистоту дерева и согласовать выбранный способ переноса. Для отдельного завершённого коммита: git cherry-pick <SHA>. Для серии коммитов использовать согласованный диапазон или merge ветки, не смешивать эти способы для одних изменений.

После переноса проверить миграции, права, общий сценарий и документы. Обновить backlog и evidence. Коммит исправлений интеграции делать только после успешных проверок. Затронутые gates проходят заново на интегрированном коде; PASS в ветке функции не доказывает PASS релиза.

## Завершение и восстановление

Сначала убедиться, что изменения сохранены и перенесены в интеграционную ветку. Остановить процессы worktree, затем git worktree remove <path>. Не использовать --force для удаления незакоммиченного результата. Локальные секреты и данные сохранять отдельно, если нужны. Ветки удалять только после проверки переноса. Инструмент не удаляет checkout автоматически.
