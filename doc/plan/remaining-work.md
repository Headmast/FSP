# Что ещё нужно реализовать

**Кратко:** опубликован рабочий технический демо-сценарий, но весь обсуждённый MVP не завершён. Не хватает полного профиля, связи с демо FSP ID, зачёта проверок в приглашении, законченной помощи при заполнении, валидации уровня и комплекта сдачи. Ниже — оставшиеся работы с приоритетами и проверками.

Срез: 2026-10-11. Исходники: `02cedf8e175bab87aac7144e3154b3ca3e979b23`; последний проверенный релиз приложения: `d1efa6409715bbc6c22dc28c4659fa38509b1878`. [Аудит и доказательства](../qa/scope-audit.md), [исходный план из чата](../sources/original-mvp-plan.md), [свод требований ТЗ](../sources/requirements-map.md), [реестр задач](backlog.md).

## Как читать список

- **Обязательство плана** — прямо присутствует в исходном плане, который пользователь поручил перенести в документацию и реализовать.
- **Требование ТЗ** — есть в исходном ТЗ или письменных уточнениях. Устные идеи и стратегические гипотезы не повышают его обязательность.
- **Прямое пожелание** — пользователь сформулировал его в связанном чате; конкретное решение ниже — предлагаемая декомпозиция.
- **Развитие** — обсуждали как гипотезу либо следующий этап; это не пропущенное обязательное условие текущего демо.
- **Ограничение демо** — механизм сделан на синтетике; реальная интеграция ещё отсутствует. Пользователь прямо разрешил мок AI; прочие ограничения описаны в плане и отчёте, но отдельного явного согласия на каждое из них не найдено.

P0 — исправить перед следующей публикацией. P1 — закрыть недостающий состав исходного MVP. P2 — развитие, реальные интеграции или эксплуатационные усиления. Статус TODO не означает начало реализации; владельцы ещё не назначены. Перед работой резервировать ID, ветку, базовый SHA, порт и допустимые файлы по [правилам worktree](../development/worktrees.md).

### FIX-001 — некорректный идентификатор

**Выполнено локально:** [изменения и проверки](../responses/FIX-001-identifiers.md). Описание ниже сохраняет исходный дефект и критерии; они закрыты указанными проверками.

Сейчас `app/hiring/views.py:44` и `app/assistant/views.py:21–22` пропускают `²` через `isdigit()`. Затем ORM выдаёт ValueError и HTTP 500. Два запроса воспроизведены на изолированной SQLite; [результат](../qa/scope-audit-id.json). Большое ASCII число в этом опыте HTTP 500 не дало.

Добавить ограниченный разбор ID и одинаковое поведение для query/form параметров. Владелец: модуль hiring/assistant; файлы `views.py`, общий валидатор по согласованию с интегратором, тесты модулей.

**Готово, когда:** Unicode, отрицательное, слишком длинное и чужое ID дают документированную ошибку формы/400/404 без 500; пустой обязательный ID даёт ошибку, пустой необязательный сохраняет документированный выбор по умолчанию; корректный ID работает; запрет доступа к чужим объектам сохранён. Проверки `ID-01–03`.

### MVP-006 — профиль кандидата

Сейчас модель хранит имя, город, навыки, контакты и грейд; нет опыта, стажа, ролей, софт-скиллов и места для описания помощника. Специализация iOS/Swift задана контекстом приложения, но не представлена в профиле как часть категории. Источник: исходный план §1/§3; ТЗ PDF 4.

Добавить структурированный опыт/роли, стаж, заявленные софт-скиллы, специализацию и приватный черновик описания. Подтверждённые сведения отделить от самоописания. Владелец: profiles; модели/миграции/формы/PDF/шаблоны/тесты.

**Готово, когда:** поля сохраняются после перезагрузки и видны в собственном PDF; категория явно содержит iOS/Swift + грейд; в публичном HTML/PDF до согласия нет контактов, включая обход через новые текстовые поля; другой пользователь ничего не редактирует. Проверки `PROFILE-04–07`. Импорт/OCR PDF не обязателен: ручной ввод удовлетворяет альтернативе ТЗ.

### FIX-002 — одинаковые навыки под разными названиями

Словарь `app/profiles/skills.py` разрешает CoreData и Core Data, а `normalized()` сохраняет их разными строками. В `app/hiring/services.py` фильтр и рейтинг сравнивают эти строки напрямую; допустимый алиас может исключить релевантного кандидата.

Ввести канонические ID навыков и единый разбор алиасов для профиля, потребности, фильтра и рейтинга. Владелец: profiles/hiring.

**Готово, когда:** CoreData/Core Data дают одинаковое сохранённое представление и одинаковые фильтры/баллы; повтор алиаса не удваивает вес; неизвестное значение получает ошибку формы; контрольная выдача пересчитана. Проверки `SKILL-01–03`.

### MVP-009 — демонстрационная связь с ФСП

Сейчас fixtures выставляют статус и призовой флаг. Кандидат не привязывает ID, записи достижений отсутствуют; endpoint возвращает только статус. Мок разрешён архитектурой демо, но сам сценарий привязки всё равно нужен. Источник: план §1/§3; ТЗ PDF 3–4; письменные/устные уточнения о демонстрации.

Добавить синтетическую личность FSP ID, привязку/отвязку владельцем, события с источником, датой, дисциплиной, результатом и командным статусом. Документировать будущий адаптер: идентичность, согласие, поля, отсутствие истории, недоступность источника, происхождение данных; не приписывать ФСП неизвестную официальную схему. Владелец: profiles и отдельный адаптер; интегратор согласует маршруты.

**Готово, когда:** проходятся not_connected/no_history/demo_history и недоступность; данные имеют явную метку мока; чужая привязка запрещена; отсутствие истории не блокирует путь; достижения не меняют грейд и не суммируют бонус бесконечно. Проверки `FSP-02–06`. Реальный Keycloak/API не требуется.

### MVP-010 — свидетельство и зачтённые проверки

История/разбор есть у кандидата; работодателю доступны агрегированный рейтинг и грейд. В Invitation нет выбранных зачтённых результатов и вопросов для обсуждения, хотя это прямо вошло в исходный план §1 и §3 «Приглашение и контакты». Более сложное задание по пробелу остаётся развитием.

Показать обеим сторонам свидетельство: направление, дата, версия банка/правил, проверенные области, результат, критерии и ограничения. Работодатель выбирает, какие завершённые результаты зачесть для конкретного предложения, и что обсудить. Сохранить этот выбор снимком и показать кандидату. Владелец: assessments/hiring; общий контракт и PDF через интегратора.

**Готово, когда:** нельзя зачесть чужую/активную попытку; зачёт адресный, сохраняется с датой и не изменяет общую категорию; редактирование потребности не меняет отправленное; контакты и активные ключи остаются закрыты. Проверки `PROOF-01–04`, `HIRE-05–07`. Экономия времени найма пока не подтверждена.

### MVP-012 и QA-001 — варианты и валидность грейда

Сейчас вариант выбирается по числу собственных попыток: все новые кандидаты одного уровня получают A. Перестановка ответов не меняет набор вопросов. Проверены пороги и 12 граничных наборов, но не независимое разделение уровней и test–retest. Источник: ТЗ PDF 2–3/6/8, XLSX VS.5 и PR.1; `app/assessments/services.py:76–82`.

MVP-012: распределять варианты между новыми кандидатами, сохранять выданный снимок, историю выдач и покрытие областей; описать ограничения двух вариантов и последующей ротации. QA-001: подготовить независимо заданные синтетические уровни/ответы, повторные A/B, протокол проверки вопросов и фактические таблицы согласованности/ошибок/разделения. Не определять эталон тем же алгоритмом, который проверяется.

**Готово, когда:** контрольная когорта новых кандидатов получает оба варианта без изменения состава активной попытки; границы и повторные старты проходят; публикуется test–retest, сопоставление A/B, разделяющая способность и обнаруженные неоднозначности. Метод, размер набора и критерии фиксируются до запуска; провалы не скрываются. Проверки `ASSESS-08–11`, `VALID-01–03`. Это синтетическая валидация, а не доказательство психометрической надёжности на реальных людях; прокторинг не требуется.

### MVP-013 и AI-001 — законченный путь помощника

### DOC-003 — HTTP контракты и OpenAPI

### OPS-002 и OPS-003 — эксплуатационные проверки

Cron реализован и реально восстанавливал туннель, сохраняя данные. Но зелёная доступность определяется по `/version/`: он не проверяет БД. `/health/` делает SELECT, но watchdog его не использует. Reboot в [отчёте](../qa/watchdog-results.md) остаётся NOT_RUN.

OPS-002: дополнить проверку health и безопасным чтением основного сценария; отделить отказ приложения/БД от отказа туннеля, чтобы не перезапускать исправный туннель из-за повреждённой базы. OPS-003: провести восстановление после контролируемого reboot на изолированном стенде, затем по согласованному окну на сервере; текущий аудит сервер не перезагружает.

**Готово, когда:** рабочий /version при отказе БД не даёт зелёную страницу; сбой публикации повторяется без ненужного restart; отказ туннеля восстанавливается; reboot возвращает приложение/URL и сохраняет состояние. Проверки `OPS-01–04`. Готовый cron и непроведённая reboot-проверка — разные статусы.

## Порядок продолжения и quality gates

1. FIX-001 и OPS-002: убрать воспроизведённую ошибку и ложную зелёную доступность.
2. Параллельно: profiles/accounts (MVP-006/008/009), hiring (MVP-007/010/011), assessments (MVP-012/QA-001). Общие миграции, маршруты, зависимости и шаблоны объединяет интегратор.
3. MVP-013/AI-001, DOC-003 и DEL-001 — после стабилизации полей и контрактов. Следующие этапы интеграций/гипотез не подменяют закрытие P1.

| Gate нового объёма | Проверки | Условие PASS | Сейчас |
|---|---|---|---|
| C1 — полные профили и согласия | ID, PROFILE, COMPANY, CONSENT, FSP | Обязательные поля/сценарии сохранены, права и приватность не нарушены | NOT_RUN |
| C2 — содержательный найм | PROOF, HIRE, MATCH, AI | Свидетельство/зачёт/объяснения/черновики работают сквозным путём | NOT_RUN |
| C3 — методика оценки | ASSESS, VALID | Варианты распределяются, независимая синтетическая валидация имеет фактические результаты и ограничения | NOT_RUN |
| C4 — комплект и переносимость | API, DELIVERY, чистый worktree | Контракты/материалы соответствуют коду, доступны из clone и проверены | NOT_RUN |
| C5 — эксплуатация | OPS выбранного этапа | Health, публикация и восстановление проверены; reboot входит только в отдельный P2 этап OPS-003 | NOT_RUN |
| C6 — выбранная реальная интеграция | Проверки INT конкретного этапа | Есть живой результат и негативные сценарии, без секретов в evidence | NOT_RUN / этап отложен |

Исторические P0/G1–G6 не переписываются: они относятся к конкретному демо-коммиту и прежним сценариям. Они не подтверждают C1–C6 и весь исходный план. После каждого успешного этапа: актуальные проверки, evidence с SHA, документы/backlog, `scripts/check_docs.py`, `git diff --check`, проверка staged diff, отдельный коммит. После интеграции повторить затронутые проверки. Процент готовности и срок завершения без оценки новых задач не заявляются.
