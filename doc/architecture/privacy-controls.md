# PROD-004 · Отзыв доступа, очистка профиля и удаление аккаунта

Статус: **DONE**. Сервер, миграции, restore fence, контракты, clean clone/browser26 и live24 приняты на выпуске `11399cc`. [Итог и доказательства](../qa/PROD-004-complete.json). Это политика данного продукта, не заявление о соответствии законодательству.

## Четыре действия кандидата

| Действие | Поведение | Подтверждение |
| --- | --- | --- |
| revoke_company | Отзывает все действующие принятые контактные гранты выбранной компании; свободные тексты прежних снимков сокращаются | Собственная сессия, CSRF, неотмеченное заранее подтверждение |
| revoke_all | То же для всех компаний | Собственная сессия, CSRF, подтверждение |
| clear_profile | Очищает профиль, опыт, предпочтения, достижения, экзамены/обучение и черновики; отвязывает приглашения; удаляет токены и инвалидирует сессии | Дополнительно текущий пароль, сохраняемый точно, включая пробелы |
| delete_account | То же плюс удаление User/email входа/хеша пароля и связанных согласий | Дополнительно текущий пароль |

Очистка сохраняет email и пароль входа: пользователь может войти и заполнить профиль заново. Удаление аккаунта не сохраняет вход. Эти действия необратимы. Уже вошедшему владельцу не навязывается новое согласие на обработку или подтверждение email ради удаления. Работодатель/чужая компания не могут удалить или отозвать доступ другого кандидата. Целевой профиль определяется по сессии, не по присланному User ID.

## Гранты и старые ссылки

Invitation имеет contact_revoked_at и candidate_erased_at. contacts_allowed — общий источник решения: собственная компания, существующий кандидат, accepted, без отзыва/очистки. API invitation contacts теперь также проверяет конкретное приглашение и общий грант; прежняя проверка только accepted убрана.

После отзыва опубликованный профиль может оставаться в общей выдаче, но подробный опыт/описание/email/телефон скрыты в HTML, PDF и API. После снятия публикации отозванная компания теряет и доступ к карточке. Повтор accepted или повтор отправки старого предложения не снимает отзыв. Новое явное принятие другого приглашения может создать новый грант компании; контактная ссылка именно старого отозванного приглашения остаётся запрещённой.

После очистки/удаления старые приглашения отвязаны от Profile (candidate_id=null); старые свидетельства, результаты, API/CLI ссылки на приватные данные не возвращают их. Старые токены недействительны. session_generation инвалидирует ранее выданные сессии, сохраняя текущий пароль при очистке. Новое заполнение/подтверждение профиля не восстанавливает старые гранты. Cookie/PDF/HTML/API ответы получают no-store; уже скачанные компанией или клиентом копии сервер физически отозвать не может.

## Сокращённая история и каскады

В приглашении сохраняются технические ID компании/потребности, исходный статус и даты, контролируемые зарплата/категория/формат/тип занятости и задач. Имена/контакты, произвольные тексты, обсуждения, подробные свидетельства и неизвестные ключи снимка удаляются. У очищенного кандидата удалены и предпочтения снимка. Компания видит сокращённую запись с пометкой privacy_redacted, не ссылку на исчезнувший профиль. Статус accepted остаётся историческим результатом, а не действующим контактным правом; архивированные sent не считаются ожидающими нового ответа.

Очистка удаляет Experience/FspLink+Achievement/Attempt/LessonProgress/PracticeSession, собственные assistant Draft/Usage и ActionDraft; связанные чужие invitation.send/response черновики также удаляются, чтобы их preview/payload/apply не воскресили данные. ORM pre_delete Profile сокращает приглашения при каскадном/административном удалении, отзывает токены и сессии. Произвольные SQL вмешательства администратора не являются поддержанным пользовательским путём удаления.

Собственные поля компании и её потребностей не удаляются вместе с аккаунтом кандидата. Очистка снимков относится к связанным приглашениям; уже известные другой стороне сведения и её внешние копии не становятся технически забытыми.

## Ограничения экзамена при очистке

Удаляются вопросы, ответы, попытки и свидетельства. У сохраняемого аккаунта остаются только ограниченные технические сроки 7/30 дней и A/B для противодействия обходу повторов. Та же категория может повторяться после семи дней; смена — после прежнего 30-дневного окна. Очистка активного теста не даёт немедленно перебрать новый вариант. Последний вариант хранится не дольше 30 дней, без баллов/заданий/ответов, затем удаляется maintenance. Это не подтверждённый грейд профиля.

## Журнал вне резервной БД

PRIVACY_LEDGER_PATH по умолчанию находится рядом с DATABASE_PATH, вне SQLite backup. В production это shared/privacy-ledger.jsonl, права 0600. Он содержит только UUID запроса, User ID, HMAC идентичности, действие, Company ID и время; имён/email/телефонов/паролей нет. Nonce нельзя повторно использовать для другого субъекта/действия. Запрос записывается с file lock/fsync до изменения БД; затем транзакция создаёт PrivacyReceipt. Если процесс прервался, следующий вход/startup/maintenance завершит уже подтверждённый запрос. Receipt не даёт повторно очистить заново заполненный профиль.

После восстановления БД журнал применяется **до выдачи данных**. Старый backup без receipt не воскресит прежние контакты/токены/профиль. Существующий receipt сохраняет новую информацию, добавленную после принятой очистки. При недоступном/повреждённом журнале запросы закрываются 503. HMAC зависит от SECRET_KEY: поддержанный restore сохраняет ключ и внешний журнал; ротация ключа требует отдельного переноса идентичностей журнала.

privacy-floor-v1 переживает очистку журнала. Текущие run_app/deploy отказываются работать/публиковать код с более старой версией приватности. Администратор не должен откатывать приложение до этой функции, удалять floor или восстанавливать каталог shared целиком из старого архива. Это ограничения поддержанного runbook; произвольный root-доступ невозможно ограничить прикладным кодом.

## Сроки и обслуживание

Продуктовые значения: сокращённая история и журнал/receipts — **180 дней**, собственные SQLite backups — **7 дней**, технические ограничения экзамена — максимум **30 дней**. Запросы на очистку применяются немедленно к выдаваемым данным. secure_delete включён; maintenance выполняет WAL checkpoint/truncate. При busy старые WAL страницы очищаются следующим успешным запуском, не ценой остановки чужих процессов.

`uv run python app/manage.py privacy_maintenance --reconcile-only` — обязательный restore guard после migrate и до startup. Полная команда дополнительно удаляет истёкшие отвязанные приглашения, ledger/receipts, экзаменационные ограничения и только собственные backup файлы с серверным timestamp-именем; чужие файлы/симлинки не удаляются. Файлы БД/backup закрываются 0600, каталог backup 0700. Установленный watchdog вызывает maintenance ежедневно; настоящий cron, `privacy_sweep_day`, режимы файлов и запрет downgrade подтверждены на сервере.

Реальная проверка политики на отдельной SQLite БД: `uv run python scripts/check_privacy_restore.py`. Она фактически копирует старую БД, восстанавливает её, применяет fence, проверяет отсутствие canary в текущих SQLite bytes после WAL truncate, сроки и сохранность посторонних файлов. Это не приёмка reboot или всего OPS-004 на VPS.

## Интерфейсы и расширение

Веб: /profile/privacy/. API: только GET /api/v1/me/privacy. CLI: fsp privacy show. MCP: fsp_get_privacy_status — read-only. У API/MCP нет delete/erase/revoke/apply действий. Ответ приглашения включает nullable candidate_id, contact_revoked_at, candidate_erased_at, privacy_redacted. [HTTP схемы](../api/contracts.md).

Новая модель с данными кандидата должна включаться в очистку и restore/retention проверки до своей приёмки. Это относится к будущим заданиям, чатам, ATS и исполнению кода. Реальные интеграции/пилот/ручной диктор не закрываются этим этапом.
