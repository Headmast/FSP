# PROD-001 · Предпочтения и условия до контакта

Кандидат выбирает допустимые форматы работы, виды занятости и интересующие типы задач. Поля необязательны. Пустое поле — неизвестное предпочтение, не «готов к любому варианту». Обязательных зарплатных ожиданий кандидата нет. Предпочтения видны в доступном работодателю профиле и PDF до принятия предложения; контакты и свободные приватные тексты по-прежнему закрыты.

## Поля и справочники

| Сторона | Поле | Значения | Пустое значение |
| --- | --- | --- | --- |
| Profile | preferred_work_formats | remote, office, hybrid | [] — неизвестно |
| Profile | preferred_employment_types | full_time, part_time, project, internship | [] — неизвестно |
| Profile | preferred_task_types | development, testing, support, architecture, mentoring | [] — неизвестно |
| Need | work_format | remote, office, hybrid | Обязательное существующее поле |
| Need | employment_type | full_time, part_time, project, internship | '' — неизвестно |
| Need | task_types | development, testing, support, architecture, mentoring | [] — неизвестно |

Это фиксированный небольшой справочник, а не свободный текст и не новая шкала компетенций. Организация выбирает все существенные типы задач; обязанности описывает отдельно в tasks. Задачи из свободного текста автоматически не распознаются. Заявленный интерес к архитектуре или наставничеству не подтверждает способность выполнять эти задачи.

## Сравнение conditions-v1

Для каждой из трёх осей формируется ровно одна строка:

- **Неизвестно**: отсутствует выбранная потребность либо значение хотя бы у одной стороны. Два пустых списка не совпадают.
- **Совпадение**: все указанные работодателем условия этой оси входят в список кандидата. remote совпадает с [remote, hybrid]; никакие дополнительные значения не подразумеваются.
- **Противоречие для уточнения**: хотя бы одно условие работодателя не входит в явный выбор кандидата. Для нескольких типов задач частичное пересечение не называется полным совпадением.

Пример: кандидат [development, testing], потребность [development, support] → противоречие по типам задач, при этом видны оба списка. Это повод уточнить предпочтения, не запрет отправить предложение. Потребность без занятости → неизвестно даже при выбранной полной занятости кандидата.

В JSON объяснение содержит conditions: version, matches, conflicts, unknown, note. Строка: key/label, candidate/required (коды), candidate_labels/required_labels, reason. Три группы одинаковы в вебе, PDF и token API; MCP получает только проверенные каталожные значения. Неизвестные, некорректные и произвольные значения legacy данных не попадают в DTO. Поля условий не участвуют в рейтинге 85/10/5, не меняют грейд и не открывают контакты.

## Поиск и PDF

Фильтр conditions требует выбранной собственной потребности:

| Значение | Результат |
| --- | --- |
| Не указан | Все кандидаты после прежних фильтров категории/навыка/ФСП |
| compatible | Нет известных противоречий; неизвестные условия допустимы и показываются |
| matched | Все три оси указаны обеими сторонами и совпадают |
| conflicts | Есть хотя бы одно явное противоречие |

Пустая выдача сохраняет фильтры; кандидаты другой категории или без подтверждения не добавляются. Неподдерживаемый фильтр/фильтр без потребности: ошибка формы, в API 400. Чужая потребность: 404.

Собственный PDF содержит предпочтения и контакты кандидата. PDF работодателя всегда содержит предпочтения; для сравнения передайте own same-grade need через `?need=<id>` в вебе или `?need_id=<id>` в API. В CLI: `fsp candidates resume <id> --need-id <id> --output result.pdf`. Контакты требуют принятого предложения именно этой компании; API дополнительно требует CLI contacts.read и with_contacts=true. MCP не получает PDF или контакты.

## Снимок и изменения

При отправке сохраняются work_format_code, employment_type, task_types, candidate_preferences и conditions_version. Карточка предложения обеих сторон и API вычисляют conditions-v1 по этому снимку, а не по текущему профилю/Need. Изменение кандидатом предпочтений, редактирование потребности и повторная отправка не переписывают условия прежнего приглашения. У старого приглашения, в котором нет preferences, все предпочтения неизвестны; контакты не открываются новым сравнением.

Смена потребности в карточке выполняется GET формой «Показать сравнение условий». POST отправляет выбранную и уже показанную потребность. Повтор/stale/expiry/CSRF и владение объектов контролируются прежними общими сервисами; изменение предпочтений делает ранее подготовленный invitation.send черновик stale.

## CLI, MCP и черновики

`fsp candidates search --need-id <id> --conditions matched --json` выдаёт сравнение до контакта. API catalog публикует справочники и feature conditions-v1. Подготовка profile.update принимает новые preferred_* списки; need.create/update — employment_type/task_types. MCP использует типизированные Literal справочники; произвольный текст, контакты и apply отсутствуют.

В браузерной форме отсутствие checkbox/list очищает список до []; в частичном V2 payload отсутствие поля сохраняет значение, явный [] очищает. Сохранение происходит после явного веб-подтверждения. Помощник на моках видит только безопасные группы условий и сообщает конфликт/неизвестное; не делает вывод о подтверждённых навыках.

## Миграции и границы

profiles/0006_work_conditions и hiring/0004_work_conditions добавляют поля со значениями неизвестно для существующих записей. Существующие категории, зарплаты, публикации и accepted снимки сохраняются. Проверка `uv run python scripts/check_conditions_migration.py` создаёт старую схему в изолированной временной БД, обновляет её и удаляет стенд; чужую или production БД не использует.

Отзыв ранее раскрытых контактов и удаление данных остаются PROD-004. Настоящий пилот/ручной диктор/SMTP/FSP/Yandex не закрываются этим этапом. Справочник задач покрывает только этот MVP; расширение справочника требует версии правил и независимой приёмки.
