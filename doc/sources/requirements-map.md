## Обязательное ядро и допуски

| Правило | Статус и точная опора |
| --- | --- |
| Собственная платформа, прямое взаимодействие кандидата и работодателя; инициатива работодателя | Обязательно: ТЗ PDF 2–3 / печатные 1–2. Витрина сторонних вакансий не является задачей. XLSX FTT.6, A15:B15: парсинг допустим для тестовых данных, не как продуктовая механика. |
| Два кабинета, профиль кандидата, профиль компании, описание потребности, подбор, поиск, адресные приглашения | Минимум MVP: ТЗ PDF 4–5 / печатные 3–4. Приглашение не обязано ссылаться на опубликованную вакансию. |
| Профиль/резюме вручную **или** загрузка PDF с автораспознаванием; генерация стандартизированного PDF-профиля | ТЗ PDF 4 / печатная 3. AI-парсинг — альтернатива форме, не обязательный способ заполнения. Генерацию PDF-профиля не исключать молча из полноты ТЗ. |
| Опрос по IT-направлению и специализации, самостоятельный выбор заявленного грейда, первичный тест | Обязательный путь: ТЗ PDF 2, 4 / печатные 1, 3. XLSX VS.1 A5:B5, VS.5 A9:B9, FTT.4 A13:B13. |
| Категория = специализация + подтверждённый тестом грейд | Достаточная модель: XLSX FTT.3 A12:B12. Грейд — уровень навыков, не число лет стажа: VS.1 A5:B5. |
| Результаты теста и достижения ФСП влияют на силу профиля/ранг внутри категории; выдача объясняет соответствие потребности | ТЗ PDF 5 / печатная 4; XLSX E08 A1:B1: достижения не заменяют тест. Все дисциплины одинаково приоритетны; релевантность дисциплины роли можно учитывать как необязательную идею. |
| Первичный грейдовый тест под категорию, не под конкретную вакансию | XLSX VS.5 A9:B9. Вакансионные задания — отдельный необязательный блок. Упоминание в ТЗ «нескольких описаний вакансий» не следует превращать в назначение грейда по каждой вакансии. |
| Устойчивость к распространению заданий, сопоставимость сложности и объективность оценки | ТЗ PDF 2–3 / печатные 1–2. Просто уникальная генерация LLM проблему не решает. Антисписывание отдельной функцией не обязательно, большой плюс: XLSX FTT.4 A13:B13. |
| Провал теста не понижает грейд принудительно; можно добровольно тестироваться ниже/выше; смена ограничена по времени | ТЗ PDF 3 / печатная 2. Три месяца — пример, не установленный срок. Статус «грейд не подтверждён» допустим: XLSX FTT.4 A13:B13. Не вводить принудительную демоцию по неудачной попытке из спорного устного примера. |
| Фильтры: специализация, грейд, категория, стек, наличие подтверждённых достижений ФСП; уточнение без потери подборки | ТЗ PDF 4–5 / печатные 3–4. |
| Зарплата в вакансии **и приглашении** обязательна: диапазон от–до в рублях, видимый до общения | ТЗ PDF 5 / печатная 4, §2.2(1). Q&A §2 уточняет: gross/net непринципиально, но явно подписать. XLSX отдельного ответа о зарплате нет. Зарплатные ожидания кандидата ТЗ не требует. |
| Приглашение: предложение, вилка, компания, способ связи; контакты кандидата закрыты до принятия приглашения или собственного отклика | ТЗ PDF 5 / печатная 4, §2.2(2). XLSX VS.4 A8:B8 разрешает ФИО и прошлые места работы: запрет касается контактов, полная анонимность — выбор команды. |
| Обе стороны видят актуальные статусы своих приглашений/откликов | ТЗ PDF 5 / печатная 4, §2.2(3). Кандидат не видит данные других кандидатов: PDF 4. |
| Email-регистрация с подтверждением адреса | **Явно обязательно**: ТЗ PDF 5 / печатная 4, §2.2(4). Q&A §7 «скорее всего, не обязательно на демо» — предварительная устная оговорка, XLSX её не подтверждает. В отчёте сохранить требование; не считать email-only российских доменов установленным запретом. |
| Приватность, согласие на обработку/публикацию, роли, защита доступа, безопасные пароли и токены | ТЗ PDF 4 и 7 / печатные 3 и 6. Ссылаться как на требования ТЗ, не как на юридическое заключение. Удаление/отзыв доступа — продуктовые дополнения, если отдельно не определены. |
| Связь профиля с FSP ID; корректный профиль без истории ФСП | ТЗ PDF 3–4 / печатные 2–3. API, схема и реальные данные не выдаются: PDF 7 / печатная 6. Реальную интеграцию заменить явно подписанной демонстрацией и архитектурной схемой, не исключать сам сценарий связи из MVP. |
| Охват MVP | XLSX VS.2 A6:B6: одной категории достаточно, несколько — плюс. WA.1 A16:B16: 2 специализации × 2 грейда достаточно, широкий справочник баллов сам по себе не даёт. Q&A допускает одну специализацию. ТЗ просит основные направления, поэтому одну роль следует обозначить выбранным срезом и объяснить. |
| Свой тестовый набор, процедура и фактические результаты валидации | ТЗ PDF 3, 6, 8 / печатные 2, 5, 7. XLSX PR.1 A4:B4: test–retest грейдов и разделяющая сила, синтетические кандидаты допустимы. Синтетика не доказывает экономию времени в реальном найме. |

Желательны/не обязательны для MVP: публикация вакансий и самостоятельные отклики, регулярные короткие задания работодателя (ТЗ PDF 4–5); ATS, защита от фиктивных вакансий — концепция после MVP (PDF 3–4; XLSX FTT.5 A14:B14); мобильная адаптация (PDF 7–8); реальный Keycloak, микросервисы, Docker — ориентиры/плюсы (PDF 3, 6–7). Подробное API и инструкция воспроизводимого запуска входят в обязательную документацию; в §3.5 есть более конкретная рекомендация OpenAPI.

Вес критериев: новая механика подбора 35%, тестирование/валидация/категоризация 25%, UX 10%, техпроработка 7%, полнота/документация 6%, дополнительные функции 7%, презентация 10% (ТЗ PDF 8–9 / печатные 7–8). Приоритет исследования: доверие к подтверждениям и адресное приглашение, затем качество оценки; не переполнить MVP соревнованиями и ATS.

## Уточнения и противоречия, которые нужно явно помечать

| Внутренняя/устная формулировка | Как трактовать в отчёте |
| --- | --- |
| Q&A §3: «ожидают российские модели» | Письменный XLSX VS.3 A7:B7 уточняет: облачные LLM, **включая зарубежные**, допустимы; предпочтительнее открытые модели. Риски передачи ПДн предусматривает команда. Не ставить российскую модель обязательным требованием. |
| Q&A строка 123: задачи соревнований как «сильный буст грейда» | ТЗ и XLSX E08, VS.1, FTT.4 закрепляют грейд по тесту. Прошлое достижение не повышает грейд автоматически; использованная в тесте задача может дать свидетельство только в рамках оценочной процедуры. |
| Q&A строка 103: пример низкого балла, который «понижает» | ТЗ запрещает принудительное понижение после теста. Считать пример неприменимым без уточнения, поддержать добровольный тест ниже. |
| Q&A §7: email-подтверждение на демонстрации «скорее всего» не нужно | В письменных ответах такого исключения нет. Сохранять подтверждение email в обязательном объёме либо отдельно честно отметить ограничение демо. |
| Q&A §4: возможный будущий обязательный FSP ID | Обещание уточнения не является введённым требованием. По имеющимся документам Keycloak — ориентир, способы авторизации выбирает команда. |
| Голосовая 06.12.29: кандидат не задаёт зарплату | Допустимое продуктовое решение. Не конфликтует с ТЗ, поскольку обязательна вилка работодателя. Стратегический HTML предлагает двусторонний матч условий — это дополнительная гипотеза, а не обязательный salary-фильтр кандидата. |
| Голосовая 06.12.52: скрывать резюме/запретить парсинг | Гипотеза защиты кандидата. ТЗ обязывает закрыть контакты, XLSX VS.4 разрешает ФИО и опыт. Договорный запрет не доказывает техническое предотвращение сбора данных; поиску/объяснениям нужно оставить разрешённую часть профиля. |
| Голосовые: тесты крупных компаний, собеседования участниками высокого грейда, локальные соревнования | Идеи развития. Первичная оценка категории не должна зависеть от наличия вакансии или доступности нанимающего; peer-интервью и челленджи не включены в минимум ТЗ. |
| Стратегический HTML: «нет истории ФСП — без штрафа» | Корректный смысл: такой кандидат проходит обычный путь и не исключается. При этом ТЗ прямо предусматривает бонус подтверждённых достижений внутри категории. Не обещать, что отсутствие ФСП вообще никак не влияет на сравнительный ранг. |

## Что уже предложено стратегическим HTML как гипотеза

- **Переносимое свидетельство навыка**: задача, результат, рубрика, дата, условия и артефакт; разделение факта, самооценки и неизвестного (HTML строки 30–34).
- **Явное зачтение работодателем**: компания отмечает, какую проверку результат заменяет; это экспериментальная ставка на доверие, не уже доказанная экономия и не требование ТЗ.
- **Проверка только пробела**: короткий сценарий после принятия части свидетельств. HTML относит её к развитию после первых маршрутов (строка 60); обычная первичная оценка категории остаётся нужна.
- **Совпадение условий заранее**, приглашение с вилкой, следующий понятный шаг, раскрытие контакта после согласия (строки 34–45).
- **Узкий MVP одной роли**, синтетическое демо плюс ручной пилот, затем расширение и реальная ФСП-интеграция (строки 49–69). Реальный пилот полезен, но ТЗ позволяет синтетическую валидацию; mock связи ФСП надо оставить уже в MVP.
- **Оценка рубрикой без обещания точного универсального грейда/IRT** и проверка принятия результата 3–5 интервьюерами (строки 75–86). Это методологическая гипотеза; официальная категоризация подтверждённым грейдом всё равно необходима.

Для итогового конкурентного отчёта разделить четыре типа высказываний: «требование ТЗ», «письменное уточнение», «наблюдаемая функция конкурента с веб-источником», «продуктовая гипотеза команды». Не объявлять переносимость результатов, антиспам, приватность или обратный найм уникальными без проверки рынка.
