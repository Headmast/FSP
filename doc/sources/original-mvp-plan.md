# План реализации MVP ФСП за пять часов

**Краткий обзор.** Собираем веб-сервис обратного найма iOS-разработчика: профиль → тест → подтверждённая категория → подбор работодателем → предложение с зарплатой → согласие и раскрытие контактов. Приложение, документация, промпты, ответы и результаты проверок хранятся в `Headmast/FSP`; разработка ведётся параллельно через Git worktree.

## 1. Результат, который должен быть готов

### Основной сценарий

Кандидат регистрируется, заполняет профиль iOS-разработчика, самостоятельно выбирает Junior или Middle и проходит тест. Работодатель описывает потребность, получает объяснимую подборку и отправляет конкретному кандидату предложение. Кандидат видит компанию, задачи, зарплату и следующий шаг; после принятия его контакты открываются этому работодателю.

Центральный элемент продукта — **содержательное приглашение**: работодатель указывает, какие результаты проверки готов зачесть и что ещё хочет обсудить. Это позволяет показать пользу подтверждённого профиля непосредственно в процессе найма.

### Обязательный состав нашей версии

| Блок | Что реализуем |
|---|---|
| Регистрация | Email, пароль, две роли, подтверждение через демонстрационное письмо |
| Профиль кандидата | ФИО, контакты, опыт, стек, специализация, заявленный и подтверждённый грейды |
| Приватность | Согласия на обработку и публикацию; включение и выключение видимости профиля |
| Тестирование | iOS/Swift Junior и Middle, варианты заданий, серверная оценка, история попыток |
| ФСП | Демонстрационная привязка ID, достижения и полноценный путь без них |
| Работодатель | Профиль компании, описание потребности, поиск и фильтры |
| Подбор | Проверенная категория, детерминированное ранжирование, причины рекомендации |
| Приглашение | Условия, обязательная вилка в рублях, зачтённые результаты, следующий шаг |
| Контакты | Раскрытие после принятия только пригласившему работодателю |
| ИИ | Один помощник Yandex AI Studio для профиля, потребности и пояснения результатов |
| PDF | Стандартизированный профиль, скачиваемый самим кандидатом |
| Сдача | Веб-демо, инструкция запуска, документация PDF, презентация и резервное видео |

**Граница пятичасового объёма:** одна специализация — iOS/Swift, два уровня — Junior и Middle. Это веб-приложение для найма мобильного разработчика.

Публикацию вакансий, самостоятельные отклики, чат, исполнение Swift-кода на сервере, прокторинг, регулярные задания компаний, ATS и реальный Keycloak переносим в следующий этап.

**Согласованные ограничения демо:**

- Письма демонстрационные: реальное владение email не подтверждается. Это явно отмечается как ограничение относительно ТЗ.
- Достижения ФСП синтетические и подписаны соответствующим образом.
- HTTPS-адрес временный и зависит от работающего туннеля.
- Живой Yandex API ещё требует успешной проверки с ключом: текущий запрос с VPS завершился таймаутом.

### Правила хранения материалов

- Каждая задача получает уникальный идентификатор, например `assessment-001`.
- Промпт сохраняется в `doc/prompts/<task-id>.md`, итоговый ответ — в `doc/responses/<task-id>.md`.
- В начале материала указываются дата, задача, ветка, исходный коммит и связанные документы.
- Ответ содержит итог работы, решения, изменения и фактические проверки.
- Код и относящиеся к нему документы коммитятся вместе.
- Ключи, пароли, реальные пользовательские данные и необработанные журналы в эти материалы не попадают.
- Базы, `.env`, виртуальные окружения, временные письма, PID-файлы, кэши и серверные логи исключаются из Git.
- Рабочие промпты приложения находятся в `app/assistant/`; документационные промпты — в `doc/prompts/`.

Исходные материалы переносим выборочно: ТЗ, письменные уточнения, текстовые расшифровки и исследования. Длинные исходные записи встреч остаются вне обычной истории Git; их происхождение фиксируется в реестре источников.

### Организация worktree

Текущий проект Codex открыт уровнем выше Git-репозитория. Поэтому создание worktree выполняется с явным указанием настоящего корня через `git -C`.

| Ветка | Ответственность |
|---|---|
| `mvp/integration` | Основная интеграция, пользователи, профили, ИИ, запуск и деплой |
| `mvp/assessment` | Банк iOS-заданий, тестирование, оценка и соответствующие проверки |
| `mvp/hiring` | Потребности, подбор, приглашения и интерфейс работодателя |
| `mvp/docs-validation` | Документация, валидация, материалы сдачи |

Порядок работы:

1. Создать интеграционную ветку от текущего `main`.
2. Подготовить общий каркас, базовые модели, интерфейсы между модулями и `AGENTS.md`.
3. Сделать один bootstrap-коммит.
4. Создать остальные worktree от этого коммита в отдельных каталогах вне основного checkout.
5. Закрепить владельца каждого модуля; общие настройки, маршруты, зависимости и базовый шаблон меняет интегратор.
6. Интегрировать завершённые ветки последовательно, проверяя сценарий после каждого объединения.
7. После итоговой проверки зафиксировать релизный коммит и развернуть именно его.
8. Удалять или архивировать дополнительные worktree после сохранения и объединения работы.

У каждого worktree собственные `.env`, `.venv`, SQLite-база, временные файлы и порт. Приложение вычисляет пути относительно своего checkout. Документация автоматически присутствует в каждом worktree, поскольку входит в тот же репозиторий. Такой порядок соответствует механике [Git worktree](https://git-scm.com/docs/git-worktree).

Перед объединением в `main` проверить публикацию старого сайта. Если используется GitHub Pages, публиковать только `static-site/` отдельным workflow.

## 3. Реализация приложения

### Архитектура и запуск

Используем модульный монолит:

- Python 3.13 и Django 5.2 LTS;
- Django Templates, обычный CSS и небольшой JavaScript;
- SQLite с WAL, короткими транзакциями и режимом `IMMEDIATE`;
- Gunicorn: первоначально один процесс и четыре потока;
- ReportLab для PDF с кириллическим шрифтом;
- HTTP-клиент для Yandex AI Studio.

Точные версии зависимостей фиксируются в `uv.lock` при создании каркаса. Django 5.2 остаётся поддерживаемой LTS-веткой. [Периоды поддержки Django](https://www.djangoproject.com/download/).

На проверенном VPS `digitarium` приложение размещается в отдельном пользовательском каталоге. Gunicorn слушает свободный локальный порт, например `127.0.0.1:8011`. Пользовательский `cloudflared` открывает его через временный HTTPS-адрес.

Скрипты должны обеспечивать установку зависимостей, миграции, загрузку демоданных, запуск, остановку, просмотр состояния и восстановление. База и секреты хранятся отдельно от каталогов релизов.

Проверку доступности после закрытия SSH включаем в ранний запуск. После перезагрузки VPS восстановление ручное. Quick Tunnel меняет адрес при новом запуске и предназначен для временных демонстраций. [Cloudflare Quick Tunnels](https://developers.cloudflare.com/tunnel/get-started/quick-tunnels/).

### Основные данные и интерфейсы

Минимальные сущности:

| Сущность | Назначение |
|---|---|
| Пользователь | Email, пароль, роль, состояние подтверждения |
| Профиль кандидата | Контакты, опыт, стек, видимость, согласия, грейды |
| Профиль компании | Название, описание, контакты работодателя |
| Попытка теста | Уровень, задания, ответы, сроки, результат, версия банка |
| Достижение ФСП | Событие, результат, источник, демонстрационный статус |
| Потребность | Грейд, желательные навыки, задачи и условия |
| Приглашение | Адресат, снимок предложения, зарплата, зачтённые результаты, статус |

Заявленный и подтверждённый грейды хранятся отдельно. Самоописание, результаты теста и достижения ФСП также разделены.

HTML-формы и JSON-маршруты используют общие серверные сервисы. Отдельный слой DRF в пятичасовую версию не добавляем.

В OpenAPI описываем фактически реализованные HTTP-интерфейсы:

- регистрацию, подтверждение, вход и выход;
- чтение и сохранение собственного профиля;
- получение собственного PDF;
- демонстрационную привязку ФСП;
- начало, продолжение и завершение теста;
- сохранение компании и потребности;
- поиск и получение подборки;
- отправку, просмотр, принятие и отклонение приглашения;
- обращение к помощнику;
- состояние приложения и версию релиза.

Для каждого указываем роль, формат запроса, ответ и ошибки. Проверки принадлежности объекта выполняются сервером.

### Регистрация и профиль

- Использовать штатное хранение паролей и сессии Django.
- Защитить изменяющие запросы CSRF.
- В демо разрешить синтетические адреса в домене `demo.invalid`.
- Показать тестовое письмо только браузерной сессии, начавшей эту регистрацию.
- Сделать токен подтверждения одноразовым, со сроком 30 минут.
- Обозначить письмо: «Демонстрационное письмо; SMTP не подключён».
- Сохранить возможность переключения на SMTP настройками окружения.

Профиль заполняется вручную; ИИ предлагает черновик описания. Кандидат проверяет его перед сохранением.

Контакты хранятся в отдельных полях. В общедоступной карточке работодателя показываются разрешённые структурированные сведения, результаты проверки и достижения. Свободное резюме с потенциальными контактами до принятия приглашения не публикуется.

### Тестирование iOS/Swift

**Формат попытки:** восемь коротких заданий, 15 минут, четыре варианта ответа, один правильный.

| Область | Junior | Middle |
|---|---|---|
| Swift | Optionals, значения и ссылки | Семантика данных, протоколы, ошибки |
| ARC | Владение объектами, `weak` | Циклы удержания, замыкания |
| Асинхронность | `async/await`, обновление интерфейса | Отмена, `MainActor`, конкурирующие запросы |
| UI и данные | Состояния экрана, декодирование | Источник состояния, устаревшие ответы, обработка ошибок |

Для каждого уровня подготовить восемь заданий в вариантах A/B: всего **32 проверенных задания**. Варианты меняют существенные условия и ответы при сохранении компетенции и предполагаемой сложности.

Перед включением в банк каждое задание проверяется разработчиком. Существенные особенности версии Swift указываются в условии. Доступный локальный Swift используется для проверки исполнимых фрагментов.

Правила оценки:

- правильный ответ — один балл;
- пропущенный или неправильный — ноль;
- подтверждение уровня — минимум 6/8 и минимум 1/2 в каждой области;
- провал первичного Middle позволяет сразу попробовать Junior;
- провал повышения сохраняет прежний подтверждённый уровень;
- повтор того же теста — через семь дней;
- изменение подтверждённого грейда — не чаще одного раза в 30 дней;
- автоматического повышения или понижения нет.

Сервер фиксирует задания, порядок вариантов, версию банка, начало и дедлайн. Повторное открытие продолжает попытку; повторная отправка завершённой попытки возвращает сохранённый результат.

Показываем баллы по областям и рекомендации, сохраняя ключи банка на сервере. ИИ-помощник во время активного теста недоступен.

Эти пороги и интервалы — правила нашей версии. Два варианта позволяют продемонстрировать вариативность; ограничения небольшого банка описываются в документации.

### ФСП и подбор

ФСП подключается через отдельный демонстрационный адаптер. Поддерживаем состояния: ID не подключён, подключён без истории, есть демонстрационные достижения. Достижения влияют на ранг внутри категории, сохраняя грейд, определённый тестом.

Основная выдача содержит открытые профили с подтверждённым выбранным уровнем iOS/Swift. Неподтверждённый кандидат видит свой статус и следующий доступный тест.

Работодатель задаёт грейд и желательные навыки. Фильтры включают категорию, стек и наличие достижений ФСП. Параметры сохраняются при переходе к карточке и обратно.

Начальная формула:

```text
Ранг = 85 × доля баллов подтверждающего теста
     + 10 × доля совпавших желательных навыков
     + бонус ФСП от 0 до 5
```

Если желательные навыки не заданы, эта составляющая одинакова для всех. Бонус ФСП: три балла за участие и ещё два за призовой результат; количество событий бонус не увеличивает. При равенстве используем балл теста, затем стабильный ID.

Карточка показывает подтверждённую категорию, тестовый результат, совпадения и пробелы. Заявленные навыки отмечаются как сведения кандидата. Пустая выдача сохраняет параметры поиска и предлагает их изменить.

### Приглашение и контакты

Приглашение сохраняет снимок условий:

- компанию, роль, описание продукта и первой задачи;
- зарплату «от–до», в рублях за месяц, до вычета налогов;
- формат работы;
- результаты проверки, которые работодатель готов зачесть;
- вопросы для обсуждения;
- следующий шаг и контакт работодателя.

Зарплата обязательна: оба значения положительные, начало диапазона не превышает конец.

Статусы: `отправлено`, `принято`, `отклонено`. Просмотр фиксируется отдельно. Обе стороны видят состояние своих приглашений.

Для одной потребности и кандидата создаётся одно приглашение. Повторное действие возвращает существующий результат. Изменение потребности не переписывает отправленные условия.

Принятие открывает контакты отправителю. Отказ сохраняет их закрытыми. Проверяем это в интерфейсе и серверных ответах.

### ИИ-помощник

Используем YandexGPT Lite 5, явный URI модели и синхронный Text Generation API. Модель и формат API подтверждены [документацией Yandex AI Studio](https://aistudio.yandex.ru/ru/docs/ai-studio/concepts/generation/models), [описанием метода Completion](https://aistudio.yandex.ru/ru/docs/ai-studio/text-generation/api-ref/TextGeneration/completion).

Три режима помощника:

1. Подготовить описание профиля по введённым сведениям.
2. Превратить потребность работодателя в редактируемый черновик параметров.
3. Пояснить сохранённый результат теста и предложить темы развития.

Модель получает необходимый контекст без контактов и экзаменационных ключей. Пользователь проверяет черновики; сервер определяет грейд, порядок выдачи и права доступа.

Запрос ограничивается 15 секундами. Ошибки и некорректные ответы оставляют ручные формы рабочими. Недоступность явно отображается. Для публичного демо установить лимит десять запросов на пользователя за час.

Ключ и идентификатор каталога находятся в `.env`. Успешный запрос с VPS — обязательная отдельная проверка живого помощника.

## 4. График на 300 минут

Один разработчик работает интегратором и использует три параллельных потока агентов. Рус готовит оформление и видео; Джа — продуктовую историю, содержание защиты и проверку понятности.

| Время | Разработчик / интегратор | Параллельные потоки | Контрольная точка |
|---|---|---|---|
| **0–20 мин** | Репозиторий, каркас, зависимости, контракты, ранний запуск VPS | Подготовка структуры документов и сценария защиты | Bootstrap-коммит; проверка HTTPS, SSH disconnect и Yandex API |
| **20–80 мин** | Пользователи, профиль, согласия, тестовые письма, PDF, ФСП | Тесты: банк и движок. Найм: потребность и приглашения. Документы: требования и QA | Модули готовы к первой интеграции; ключи заданий проверены |
| **80–140 мин** | Интеграция тестирования, история и грейд; помощник | Проверки вариантов, интерфейс работодателя, первый экспорт документации | Кандидат проходит полный путь до категории; PDF читается |
| **140–185 мин** | Интеграция подбора и приглашений; обновление веб-демо | Проверка ролей, контактов и объяснений | Полный сценарий до принятия и раскрытия контактов |
| **185–230 мин** | Исправление ошибок и пограничных состояний | Фактическая валидация, проверка документов, репетиция | Основной сценарий стабилен; добавление функций прекращается |
| **230–265 мин** | Итоговый деплой, конкурентные запросы, проверка релиза | Обновление результатов QA, снимки экрана, материалы защиты | Все обязательные проверки выполнены |
| **265–290 мин** | Исправления только по обнаруженным проблемам | Запись видео, финальный PDF и презентация | Комплект сдачи готов; ссылки проверены |
| **290–300 мин** | Финальный коммит, версия релиза, проверка веб-адреса | Контроль комплектности | Зафиксирован проверенный SHA |

Документы и презентация готовятся с начала работы. Последний час используется для обновления материалов по фактическому поведению приложения.

Если первая проверка Yandex API не проходит, интеграция помощника сохраняет честное состояние недоступности; основной сценарий продолжает разрабатываться. Пункт «живой ИИ» остаётся незавершённым до успешного запроса.

## 5. Проверка, приёмка и сдача

### Проверки поведения

Обязательно проверить:

- регистрацию и одноразовый токен, включая чужую сессию;
- доступ кандидата только к собственным данным;
- отсутствие контактов до принятия и после отказа;
- раскрытие контактов только пригласившему работодателю;
- повторное и одновременное принятие приглашения;
- подмену ID попытки, балла и грейда;
- просроченную и повторную сдачу теста;
- результат 6/8 с проваленной областью;
- сохранение Junior после провала Middle;
- доступность Junior после первичного провала Middle;
- ограничения повторных попыток;
- путь кандидата без ФСП;
- отсутствие влияния ФСП на грейд;
- пустую выдачу и сохранение фильтров;
- некорректную зарплату;
- сбой ИИ и продолжение ручного сценария;
- сохранность данных после перезапуска.

На SQLite конкурентные переходы защищаются короткими транзакциями, условными обновлениями и ограничениями БД. Вызов ИИ выполняется вне транзакции; `ATOMIC_REQUESTS` выключен. Не полагаться на `select_for_update()`, который SQLite не поддерживает. [Особенности SQLite в Django](https://docs.djangoproject.com/en/5.2/ref/databases/#sqlite-notes).

### Валидация решения

Подготовить воспроизводимый набор:

- 24 синтетических кандидата: десять Junior, десять Middle и четыре с неподтверждённым уровнем;
- три потребности работодателя;
- кандидатов с достижениями ФСП и без них;
- 12 сценариев ответов: слабые, пограничные, проходные, сильные, пропуски и провал отдельной области.

Сохранить:

- аудит 32 заданий и исправленные неоднозначности;
- ожидаемые и фактические результаты оценки;
- сравнение вариантов A/B на подготовленных сценариях;
- Precision@5 для трёх потребностей;
- число нарушений обязательных условий;
- сравнение с простым подбором по ключевым словам;
- примеры ошибок и ограничения проверки.

Цель проверок правил — полное совпадение ожидаемого и фактического результата. Для выдачи внутренняя цель — Precision@5 не ниже 0,8 и отсутствие нарушений обязательных условий.

Дополнительно выполнить прогон с 25 одновременными пользователями: чтение профиля, поиск и несколько конкурентных изменений. Внутренняя цель — отсутствие ошибок сервера и блокировок БД; p95 основных операций до двух секунд без учёта генерации ИИ.

Числа являются целями команды. В отчёт записываются фактически полученные результаты. Проверка синтетики подтверждает работу правил; качество оценки реальных специалистов требует последующего пилота.

### Комплект сдачи

К завершению пяти часов в репозитории должны находиться:

- краткий обзор и подробный план;
- карта покрытия требований;
- архитектура и модель данных;
- описание тестирования, категоризации и подбора;
- схема будущей интеграции ФСП;
- OpenAPI с примерами;
- зависимости с версиями;
- инструкция запуска из свежего checkout или worktree;
- инструкция развёртывания и восстановления;
- демоданные, сценарии и фактический отчёт QA;
- промпты, итоговые ответы и журнал решений;
- документация PDF и презентация;
- сценарий и резервная запись демонстрации.

**Приёмка релиза:** из свежего worktree приложение запускается по инструкции, основной путь проходит в браузере, контакты раскрываются адресно, документы соответствуют поведению, а веб-демо показывает зафиксированный коммит. Демонстрационные письма, синтетические данные, временный адрес и состояние живого ИИ явно отражены в комплекте сдачи.
